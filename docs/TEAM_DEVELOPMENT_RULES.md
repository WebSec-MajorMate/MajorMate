# MajorMate 팀 개발 및 Git 협업 규칙

> 적용일: 2026-11-23  
> 대상 저장소: `WebSec-MajorMate/MajorMate`

## 1. 브랜치 전략

| 브랜치 | 용도 | 직접 푸시 |
| --- | --- | --- |
| `main` | 검증된 기능만 포함하는 배포 안정 브랜치 | 금지 |
| `dev` | 기능 통합 및 팀 테스트 브랜치 | 금지 |
| `feat/<담당>-<기능명>` | 개별 기능 개발 브랜치 | 해당 작업자만 가능 |
| `fix/<영역>-<문제명>` | 버그 수정 브랜치 | 해당 작업자만 가능 |
| `docs/<문서명>` | 문서 변경 브랜치 | 해당 작업자만 가능 |

- 모든 개발은 `dev`에서 최신 내용을 받은 뒤 기능 브랜치를 만들어 시작한다.
- 기능 브랜치는 하나의 독립적인 기능 또는 수정만 담는다.
- 기능 브랜치에서 `dev`으로, 검증된 `dev`에서 `main`으로 순서대로 병합한다.
- `main`과 `dev`는 보호 브랜치로 설정하고, 직접 푸시·강제 푸시·승인 없는 병합을 허용하지 않는다.

## 2. 작업 시작 절차

```bash
git switch dev
git pull origin dev
git switch -c feat/<담당>-<기능명>
```

- 작업 전에 이슈 또는 팀 합의로 작업 범위와 담당자를 분명히 한다.
- 다른 팀원의 도메인 파일을 수정해야 하면 사전에 해당 담당자에게 알린다.
- 커밋은 되돌리기 쉽도록 작은 단위로 작성한다.
- 커밋 메시지는 변경 의도가 드러나도록 작성한다. 예: `feat: add study application approval`.

## 3. Pull Request 규칙

모든 병합은 Pull Request(PR)를 통해서만 수행한다.

1. 기능 작업을 마치면 원격에 브랜치를 푸시하고 `dev` 대상 PR을 생성한다.
2. PR에는 목적, 주요 변경 파일/동작, 테스트 방법과 결과, 보안 영향 및 주의사항을 작성한다.
3. 작성자는 최소 한 명의 팀원에게 리뷰를 요청한다. 작성자는 자신의 PR을 승인 또는 병합하지 않는다.
4. 리뷰어의 피드백을 반영하고 필요한 테스트가 통과한 뒤 승인받는다.
5. 승인 후에만 `dev`에 병합하며, 병합 후 기능 브랜치는 삭제한다.
6. 배포 또는 발표 전에는 `dev`에서 통합 테스트를 마친 뒤, 별도 PR로 `main`에 병합한다. 이 PR도 동일하게 리뷰와 승인을 거친다.

## 4. PR 체크리스트

- [ ] 최신 `dev` 변경사항을 반영했고, 불필요한 충돌이 없다.
- [ ] 변경 범위가 PR 제목과 설명에 맞고 관련 없는 변경이 없다.
- [ ] `npm.cmd run build` 또는 변경 범위에 맞는 검증을 수행했다.
- [ ] 인증이 필요한 기능은 비로그인 접근을 차단한다.
- [ ] URL/폼의 ID만 신뢰하지 않고 서버에서 세션 사용자 권한·소유권을 확인한다.
- [ ] 사용자 입력은 Zod로 검증하며, NoSQL 쿼리에 객체 형태의 입력을 그대로 사용하지 않는다.
- [ ] 사용자 입력을 HTML로 삽입하지 않아 XSS 위험이 없다.
- [ ] 환경 변수, 비밀번호, 토큰, 개인정보가 커밋에 포함되지 않았다.

## 5. 충돌 및 긴급 수정

- 충돌 해결이 어렵거나 공통 파일 변경이 겹치면 임의로 덮어쓰지 말고 관련 담당자와 먼저 조율한다.
- `main`의 긴급 수정도 `fix/` 브랜치와 PR을 사용한다. 수정 PR은 먼저 `main`에 병합하고, 동일 변경을 `dev`에도 반드시 반영한다.
- 규칙 변경은 팀 논의 후 이 문서와 `PROJECT_SPEC.md`에 함께 반영한다.
