# 1:1 쪽지 MVP

## 사용 흐름

1. 로그인 후 `/messages`에서 상대의 정확한 닉네임을 입력한다.
2. 두 사용자 사이의 기존 대화방이 있으면 재사용하고, 없으면 생성한다.
3. 대화방에서 최대 2000자의 텍스트 쪽지를 보낸다.
4. 상대는 쪽지함 또는 대화방의 ‘새 쪽지 확인’을 눌러 확인한다.

닉네임 기반 쪽지이며 실시간 수신, 익명 표시, 읽음 처리와 미확인 개수는 후속 작업이다. 메시지는 최신 50개씩 표시하며 ‘이전 쪽지 보기’로 이전 내역을 확인한다.

## 데이터와 권한

- 조회 함수와 Server Action에서 각각 세션을 확인한다.
- 대화 조회·전송에는 대화방 ID와 함께 세션 사용자의 참여자 조건을 적용한다.
- 발신자는 세션, 수신자는 대화방에서 결정한다. 폼의 발신자·수신자 값은 사용하지 않는다.
- 정렬된 두 사용자 ID를 `participantKey`로 저장하고 고유 인덱스로 중복 방 생성을 막는다. 기존 키 없는 방은 대화를 시작할 때 재사용한다.
- 새 방 생성 전에 `MessageRoom.init()`으로 인덱스 준비를 기다린다. DB 계정은 인덱스 생성 권한이 필요하다.
- 쪽지와 대화방 미리보기는 MongoDB 트랜잭션으로 함께 저장한다. 프로젝트에서 사용하는 Atlas 또는 replica set 환경이 필요하며 standalone MongoDB는 지원하지 않는다.
- 본문은 일반 JSX 텍스트로 렌더링한다.

자동 테스트는 인증·DB 어댑터를 대체하여 실제 서버 모듈의 권한 검사, 입력 검증, 수신자 결정, 방 재사용과 중복 생성 충돌 처리를 확인한다. 실제 Atlas 트랜잭션·인덱스와 브라우저 동작은 아래 통합 시나리오로 별도 확인한다.

### 수동 통합 시나리오

- A/B/C 세 계정을 서로 다른 브라우저 세션으로 로그인한다.
- A가 B의 닉네임으로 대화를 시작하고, B도 A의 닉네임으로 시작했을 때 같은 방인지 확인한다.
- 동시에 대화를 시작해도 DB에 해당 `participantKey` 방이 하나만 생성되는지 확인한다.
- 양방향 전송 후 새 쪽지 확인을 눌러 본문, 한국 시간 표시, 마지막 메시지 미리보기를 확인한다.
- C가 A/B 방 주소에 접근하면 내용을 볼 수 없는지 확인한다.
- C 세션으로 해당 방의 전송 액션을 호출해도 메시지가 저장되지 않는지 확인한다.
- 공백, 2001자 본문, 잘못된 방 ID, 본인 닉네임, 존재하지 않는 닉네임을 거부하는지 확인한다.
- `<script>alert(1)</script>`가 실행되지 않고 텍스트로 표시되는지 확인한다.
- 51개 이상 메시지에서 이전 내역·최신 내역 이동을 확인한다.
- DB 연결 실패 시 오류 안내가 표시되고 전송 실패 시 입력이 유지되는지 확인한다.
